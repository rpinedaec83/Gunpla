# UX Pattern 05: Identity, Authentication, and SSO Journey

Status: Draft template
Owner: Product, UX, and Security
Last Reviewed: TBD

## Intent
A resilient, security-aligned authentication and authorization user experience for enterprise portals, SaaS applications, and customer web products.

This pattern handles the full lifecycle of identity interaction: corporate Single Sign-On (SSO / SAML 2.0 / OIDC), credential-based sign-in, passwordless and passkey alternatives, multi-factor authentication (MFA) step-up challenges, session expiration, and recovery flows.

## Preferred Description
Hybrid identity and sign-in journey featuring email-based identity discovery (smart routing to enterprise SSO or local auth), accessible credential forms, dedicated MFA verification challenges, graceful session expiration alerts, and deep-link destination preservation.

## Evidence-Informed Rules (Authentication and Identity UX)
Use these rules when this pattern is selected:
- Support email domain discovery to seamlessly route enterprise users to their corporate IdP (Entra ID, Okta, Google Workspace) without confusing consumer-style multi-button login walls.
- Avoid account enumeration vulnerabilities: error messages for failed credentials or recovery lookups must use uniform wording that does not reveal whether an email address exists.
- Never clear user input fields unnecessarily on validation failure, except for sensitive password and one-time code inputs.
- Clearly differentiate primary enterprise SSO action from secondary local credential sign-in.
- Support password visibility toggling, password manager autofill, and WebAuthn/passkey capabilities where available.
- Treat MFA as a distinct, focused verification step rather than cramming codes into the initial sign-in view.
- Preserve intended destination URLs across redirects, so users land on the page they originally requested after authenticating.
- Provide a polite pre-expiration session modal before terminating active user sessions, giving users a chance to extend without losing unsaved form data.
- Meet WCAG 2.1 AA accessibility requirements for all form inputs, error summaries, and screen reader announcements.

## Preferred Structure
1. Clean brand-anchored card layout with domain discovery
2. Primary enterprise SSO authentication route
3. Fallback or consumer username and password form
4. Dedicated Multi-Factor Authentication (MFA) verification challenge
5. Session expiration warning modal with extend option
6. Self-service password reset and magic link recovery journey

## Discovery and Authentication Flows

### 1. Enterprise SSO Flow (IdP-Initiated or SP-Initiated)
- User enters enterprise email.
- System detects tenant domain binding.
- UI transitions smoothly to redirecting state with an accessible progress indicator.
- User is directed to identity provider (e.g., Azure Entra ID, Okta).
- Upon successful assertion, user is redirected back to the verified application callback endpoint and routed to original destination.

### 2. Local Credential Flow
- For non-SSO users, input expands or unlocks password field.
- Password field includes client-side syntax validation (length, complexity) before submission.
- Optional passkey / WebAuthn button allows biometric or hardware key sign-in.
- Rate limiting and CAPTCHA / bot detection trigger gracefully after repeated failures.

### 3. Step-Up and MFA Flow
- Required when accessing privileged resources, administrative sections, or after initial password sign-in.
- Supports TOTP (Authenticator apps), FIDO2 WebAuthn keys, or SMS/email fallback when configured.
- Provides accessible countdown timers for temporary codes and clear resend options with cooldowns.

### 4. Session Expiration and Graceful Re-authentication
- Proactive client-side warning displayed at least 2 minutes prior to session invalidation.
- Silent token refresh via background OAuth refresh tokens when active interactions continue.
- In-place modal re-authentication preserves current form state and unsaved drafts if session expires while typing.

## Error Handling and Security Feedback
- Uniform error messages: "Invalid email or password" prevents account harvesting.
- Explicit lockout warnings: Inform users when account is temporarily throttled, providing self-service unlock or administrator contact options.
- Transparent network error recovery: If identity provider is unreachable, display status check links and clear escalation guidance.

## When to Use This Pattern
- Any enterprise, SaaS, or commercial web application requiring user accounts.
- Applications supporting hybrid user populations (internal corporate SSO users plus external clients or partners).
- Regulated applications requiring multi-factor authentication and explicit session governance.

## When Not to Use This Pattern
- Public anonymous landing pages or read-only documentation portals.
- Command-line interfaces or machine-to-machine API integrations (use token-based service principals instead).

## Common Failure Modes
- Trapping users on a generic login screen without preserving their deep-link destination URL.
- Exposing whether an email exists through differing error responses on password vs email lookups.
- Forcing full page reloads that discard filled form fields when session timeouts occur.
- Omitting keyboard navigation on MFA digit inputs or passkey triggers.
